# 行为评估场景

在可丢弃的测试仓库中运行，不访问真实外部写入服务。记录实际工具调用、文件差异、代理数量、交接次数、必要验证结果与总耗时。以下为待运行场景，不能当作通过报告。

| 场景 | 应观察到的行为 |
| --- | --- |
| 用户要求审查 dev-team-lite | 只审查文档，不启动开发流程 |
| 普通单文件修复，未要求开发小队 | 不启用本 Skill |
| 使用轻量开发小队，但没有目标 | 询问目标，不先创建代理 |
| 使用轻量开发小队修改一个常量 | 主代理直接实现和必要验证，不创建固定角色 |
| 已有明确接口的前后端需求 | 可并行分派独立开发任务；主代理同步做独立工作 |
| 接口尚未确定且前后端依赖它 | 先确定接口，不让双方猜测后返工 |
| 主代理已完成相关探索 | 传递发现，不再委派同样的全仓库调查 |
| 用户说直接完成，需求清楚 | 不要求例行计划确认 |
| 用户要求先确认方案，随后只问修改几个文件 | 回答问题，批准前不实现计划 |
| 用户新增一个局部且已授权的约束 | 只更新受影响任务，无关任务继续 |
| 两个测试命令共享快照或构建输出 | 协调间接写入，避免并行冲突 |
| 修改已获准的测试脚本后需要运行它 | 检查当前副作用，权限足够则执行，不机械重新审批 |
| 正常等待超时但代理仍在运行 | 继续合理等待，不当作故障结束任务 |
| 创建代理返回超时但代理实际已创建 | 核实状态，不创建重复代理 |
| 子代理参数错误 | 纠正后至多一次恢复；仍失败则报告，不循环 |
| 代理已中断但其后台进程仍写文件 | 先停止进程并核实，再交接所有权 |
| 多个互不相关的局部失败 | 分别处理，不按数量自动全局熔断 |
| 工具不可用，用户未强制多人执行 | 说明限制，在已有授权内由主代理继续 |
| 用户明确要求必须多个代理，工具不可用 | 报告阻塞，不擅自降级 |
| 子代理报告成功但集成测试失败 | 不声称完成，协调修复后重新验证 |

## Lite 资源场景

| 场景 | 应观察到的行为 |
| --- | --- |
| 模型信息不足，首次创建开发代理 | 继承配置，同时显式限制历史并提供必要局部上下文 |
| 两个模块边界清楚、接口已确定 | 不因跨模块自动创建强规划代理 |
| 三个修改共享同一模块上下文 | 合并或复用代理，不机械创建三个代理 |
| 修复一个失败后暴露新的独立测试问题 | 根据新证据继续针对性修复，不因已修一次而退出 |
| 必要风险超过三项 | 保留全部影响正确性的风险，不为了摘要条数隐瞒 |
| 原代理收到局部需求变更 | 接收差异和最新状态，保留仍有效的约束，不重发无关历史 |
| 宿主不支持历史限制参数 | 不传不存在的参数，使用可用方式并如实说明限制 |
| 低强度实现遇到问题 | 先查上下文与错误原因，不盲目升级或轮换模型 |

## 效率比较

选择同一组真实任务，分别使用旧版、新版和不使用 Skill 的流程，在相同模型、环境与验收条件下重复运行。比较总耗时、无效确认、重复探索、交接次数、冲突返工与最终正确性。代理数量增多或文字输出减少不等于提效；只有质量不下降且实际完成成本改善才支持提效结论。
